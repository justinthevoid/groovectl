# 0.6.0-rc.5 candidate

The Windows app check found that Cider could acknowledge Pause before its state endpoint reflected the change. The adapter now performs at most four read-only state observations, with three 150 ms delays, after an accepted untargeted Play/Pause command. It sends the command exactly once. A failed read or an unobserved requested state requires inspection; no successful playback claim is synthesized from the acknowledgment.

This keeps rc.4's local player chooser, execution-host label, versioned app resource and Windows-local connection guidance. Actual rc.4 UI checks established loaded Apple Music play/pause, Cider playback with an advancing timestamp and independent library setup status. They did not establish embedded streaming, universal transport capabilities or Windows API-library authorization.

The [qualification ledger](../qualification.md) records candidate-specific checks. Remaining public distribution and player gates retain their separate scope.

## Follow-up Windows qualification

The published runtime passed real stdio catalog/library reads on Windows after an existing Groovectl authorization was privately migrated and verified with Apple. The actual Windows-local app loaded playlists/albums, opened artist → albums → songs, and controlled Cider through its footer. Fresh Chrome authorization failed before a verified connection was saved; this first-run path remains unresolved.

An explicitly approved disposable Cider queue verified targeted song playback with an advancing timestamp, Play Later append and Play Next insertion ahead of an existing upcoming recording. Cider's own UI matched the exact IDs returned through MCP. One Stop became non-playing but retained the current recording, timestamp and queue, so the documented removal behavior is not qualified. The original current recording, timestamp, paused state and modes were restored; the old history/queue was not restored. No runtime or existing release artifact changed for these follow-up checks.
